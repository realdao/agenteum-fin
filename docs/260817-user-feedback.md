## 二、原因归纳（四类根因）

**1. 工具路由缺口：stock_\* 系列不认基金代码段。**
A 股股票是 6/0/3 开头，而上交所 ETF 是 51/56/58、深交所 ETF 是 15/16/18——工具的 symbol 校验只覆盖了股票代码段。stock_profile 本身设计面向个股（PE、简介等字段），不支持 ETF 可以理解，但**报错信息没有给出替代路由**，属于可用性缺陷。推断 stock_kline、stock_financial_statements 大概率同样不认 ETF。

**2. NLU 实体识别对"指数名称"和"多字段组合"脆弱。**
"国证粮食指数"没有被识别为指数实体，而是被拆成"行业包含粮食"；"前十大权重股+PE+PB"四字段组合进一步干扰了解析。**给代码（399365）比给中文名称可靠得多**；一次问一件事比打包问可靠得多。

**3. 静默部分失败是最危险的问题。**
第 4 次查询 3 只实体只返回 1 只，响应里没有任何 errors/missing 字段提示缺失。如果我不够警觉，就会拿着 1/3 的数据直接下结论。多实体×多字段的笛卡尔积超出后端组装能力时，它选择"给多少算多少"而不是报错。

**4. 返回数据的口径与形态不可控。**
"价格走势"这类模糊表述让后端自选指标和频率：日度全量数据直接淹没上下文（小麦一项就占了约 200 行）；同一查询里不同指标频率不一致（玉米月度 vs 小麦日度）；"磷酸二铵价格"匹配到 CPRI 零售指数而非现货价。字段名缩写（`最低价[20260814]`）掩盖了真实口径，必须逐个核对。

## 三、优化建议

### A. 使用侧规范（我可以立即执行，也适合沉淀到 rules/ 或 AGENTS.md）

1. **ETF/基金一律走 `iwencai_query`（market 域），不走 stock_\* 系列**；个股基本面才用 stock_fundamental_snapshot / financial_statements。
2. **实体用纯代码**：股票/ETF 用代码（159698），指数用代码（399365），避免"简称+代码"混合写法和纯中文名称。
3. **控制查询复杂度**：单查询 ≤2 个实体、≤4 个字段；多实体多字段拆成多次并行调用。
4. **价格类查询显式指定频率和区间**（如"2026年6月以来月度"），防止日度全量数据淹没上下文。
5. **每次返回先核对 returned_count 与请求的实体数**，发现缺失立即单独补查；字段名逐个人工确认口径（区间、复权、单位、截止日期）后再引用。
6. **首次使用某个 domain 或查询返回空时，先读 `agenteum-fin://tools/iwencai-query-guide` 资源**再重试（工具描述里明确要求，我这次靠试错绕过去了，属违规操作，index 域那次失败本可避免）。
7. **域的选择需要试错预算**：指数成分在 index 域查不到但在 astock 域能查到，说明域边界与直觉不一致——重要查询失败后优先换域+换写法，而不是原样放宽。

### B. 工具侧反馈（如果能传给 agenteum_fin 提供方）

1. stock_\* 的 invalid_symbol 报错应附带路由提示："该代码疑似场内基金，请改用 iwencai_query"。
2. iwencai 部分返回时**必须**在响应中显式列出缺失实体（errors/missing 字段），消灭静默部分失败。
3. 字段名写全口径：`区间最低价[20250102-20260814](前复权)` 而非 `最低价[20260814]`。
4. 日度指标返回默认聚合为月末值或做行数截断，需要日度时由调用方显式声明。
5. index 域补齐"指数成分及权重"的标准查询路径，并在 guide 中写明推荐写法。
